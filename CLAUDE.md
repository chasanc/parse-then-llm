# parse-then-llm

Two-tier invoice extraction: a NestJS + Postgres API runs jobs through a deterministic parser (Tier 1), then an
LLM (Tier 2) only when Tier 1 is unsure. Read `README.md` for the picture and `docs/adr/` for why.

## Rules that are easy to break

- **Clean-room.** All data is synthetic, generated by `eval/generate_fixtures.py`. No real invoices, employer
  names, ticket IDs or proprietary prompts.
- **Secrets come from environment variables only.** Never write a real key into a file, test or log. Tests use
  random secrets. `.env` is gitignored; do not read or print it.
- **Empty never overwrites** (ADR 0003). The merge lives in `apps/api/src/common/merge.ts` only. Do not
  re-implement it in SQL or in an extractor.
- **The API derives `status`.** Extractors report values; they do not decide the final status.
- **Money is integer minor units.**
- **`extraction_runs` is immutable.** A trigger enforces it. Never add an UPDATE or DELETE path.
- **Applied migrations are never edited.** Add the next numbered file in `apps/api/migrations/`.
- **Adding or changing an extraction field** touches six places: use `skills/add-extraction-field/SKILL.md`.

## Commands

```
npm test -w @parse-then-llm/api                          # needs Postgres on :5440 (docker compose up -d postgres)
npm run typecheck -w @parse-then-llm/api
uv run --directory services/extractor-deterministic pytest -q
uv run --directory services/extractor-llm pytest -q
docker compose up -d --build && eval/run_eval.py         # needs .env: cp .env.example .env and set HMAC_SECRET
```

## Conventions

- NestJS constructors use explicit `@Inject(Class)`; the test runner does not emit decorator metadata.
- Tests that need a database use `startTestApp()`, which creates and drops a throwaway database. Never point
  tests at a real one.
- Python deps are managed with uv; `pyproject.toml` sets a 7-day `exclude-newer` cooldown.
- Known limits are marked with a `shortcut:` comment saying when to revisit them.
